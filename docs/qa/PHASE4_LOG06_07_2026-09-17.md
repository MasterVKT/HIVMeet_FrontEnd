## LOG-06 — Jeton FCM Android et endpoint backend

### Symptôme initial

```
E/FirebaseMessaging: Topic sync or token retrieval failed on hard failure exceptions:
  java.util.concurrent.ExecutionException: java.io.IOException: SERVICE_NOT_AVAILABLE
DEBUG fcm: No FCM token: subject=<redacted>
```

L'émulateur n'obtenait pas de jeton FCM (SERVICE_NOT_AVAILABLE). Le backend
n'avait pas de jeton enregistré pour les notifications like/match.

### Diagnostic séparé

| Composant | Statut | Preuve |
| --- | --- | --- |
| Acquisition Android (getToken) | Échec émulateur (SERVICE_NOT_AVAILABLE), OK appareil physique | emulator_run ligne 17 ; backend_run : FCM token registered pour appareil physique |
| Endpoint backend POST /auth/fcm-token | Fonctionnel | backend_run : `200` pour `POST /api/v1/auth/fcm-token` |
| Serializer FCMTokenSerializer | Valide | `fcm_token` required, `device_id`/`platform` optional |
| Persistance fcm_tokens | Fonctionnel | `add_fcm_token()` dans User model |
| Envoi notification | Fonctionnel | `send_fcm_to_user()` avec fallback `No FCM token` |

### Cause racine (frontend)

`registerTokenWithBackend()` dans `notification_service.dart` avalait
silencieusement toutes les exceptions avec `catch (_)` — aucune retry, aucun
logging, aucun backoff. Quand `getToken()` levait `SERVICE_NOT_AVAILABLE`,
l'erreur était définitivement perdue.

### Correctif frontend appliqué

**`lib/data/services/notification_service.dart`** :

1. **Retry borné avec backoff exponentiel** :
   - Maximum 3 tentatives
   - Délai : 2s, 4s, 8s (formule `2^retryCount`, plafond 30s)
   - Annulable via `sessionGeneration` : si l'utilisateur se déconnecte
     pendant le retry, la tentative est abandonnée
   - Jamais de boucle active

2. **Reset du compteur de retry** sur succès (`_tokenRetryCount = 0`)

3. **Non-bloquant** : login et navigation ne dépendent pas de FCM. L'app
   reste utilisable hors connexion ou si FCM échoue.

4. **Sécurité** : le token FCM n'est jamais logué. Seul le type d'erreur est
   traité, jamais la valeur du token.

### Endpoint backend (aucun changement requis)

Le backend FCM endpoint est déjà robuste :
- `FCMTokenSerializer` valide `fcm_token` (required), `device_id`, `platform`
- `RegisterFCMTokenView` enregistre via `user.add_fcm_token()`
- Déduplication et ownership gérés par le modèle User
- Logging redigé (`FCM token registered for user: <email:redacted>`)

### Test de non-régression

`test/android/fcm_retry_test.dart` : 4 tests validant backoff, max retries,
annulation, et sécurité (token jamais logué).

## LOG-07 — Celery/Redis explicite par environnement

### Symptôme initial

```
WARNING connection: No hostname was supplied. Reverting to default 'localhost'
DEBUG fcm: No FCM token: subject=<redacted>
```

Le broker `memory://` avec hostname implicite rendait le chemin local ambigu.
Le mode eager masquait les pannes de Redis.

### Cause racine

`settings.py` utilisait :
```python
CELERY_BROKER_URL = config('CELERY_BROKER_URL', default='memory://')
CELERY_TASK_ALWAYS_EAGER = config('CELERY_TASK_ALWAYS_EAGER', default='True' if DEBUG else 'False')
```

- Pas de distinction explicite entre dev/staging/prod
- `memory://` fallback silencieux en production si `CELERY_BROKER_URL` non configuré
- `transaction.on_commit()` non utilisé pour `send_call_notification.delay()`

### Correctif backend appliqué

#### 1. Configuration Celery explicite (`hivmeet_backend/settings.py`)

Politique par environnement :

| Environnement | Broker | Eager | Worker/Beat |
| --- | --- | --- | --- |
| Tests unitaires | memory:// (test_settings) | True | Non requis |
| Dev sans broker | memory:// (explicite) | True | Non requis |
| Recette/staging | Redis (CELERY_BROKER_URL) | False | Démarré |
| Production | Redis (CELERY_BROKER_URL obligatoire) | False | Démarré |

**En production (DEBUG=False) sans `CELERY_BROKER_URL`** : `RuntimeError` au
démarrage. Jamais de fallback `memory://` silencieux en production.

#### 2. `transaction.on_commit` pour les effets de bord

**`messaging/services.py`** — `CallService.initiate_call()` :
- Avant : `send_call_notification.delay()` appelé directement après
  `Call.objects.create()` — risquait d'envoyer une notification si la
  transaction était annulée
- Après : `transaction.on_commit(lambda: send_call_notification.delay(...))`
  — la notification n'est envoyée qu'après commit réussi

**Vérification** : `matching/signals.py` utilisait déjà `transaction.on_commit`
correctement.

### Tests backend

**`hivmeet_backend/tests/test_celery_config.py`** : 5 tests :
1. `test_settings_eager_is_true` — tests utilisent eager
2. `test_dev_broker_is_memory_when_no_broker_url` — dev sans broker → memory
3. `test_production_without_broker_url_raises` — prod sans broker → RuntimeError
4. `test_call_notification_uses_transaction_on_commit` — source contient on_commit
5. `test_matching_signals_use_transaction_on_commit` — source contient on_commit

**`messaging/tests.py`** — test `test_premium_user_can_initiate_call` corrigé :
utilise `captureOnCommitCallbacks(execute=True)` pour déclencher les callbacks
`on_commit` pendant le test.
